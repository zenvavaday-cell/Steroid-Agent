# Streaming Pipeline Design

## Overview

Streaming pipelines fail differently from batch jobs. Duplicates arrive after a consumer restart, events arrive minutes late, one partition runs hot, and a schema change breaks every consumer at once. A design is credible only when it states the delivery guarantee per hop, the event-time semantics, the state size and recovery time, and how a replay will avoid double counting.

Exactly-once is a property of a closed system (source, processing, sink), not a label you can attach to a topic. Most production designs use at-least-once delivery plus idempotent sinks and accept that duplicates are deduplicated at the last responsible point.

## When to use

- Designing a Kafka, Kinesis, Pub/Sub, or Pulsar topic and its consumers.
- Building real-time dashboards, alerting, or fraud detection.
- Choosing between at-least-once and exactly-once processing.
- Adding event-time windows and late-data handling.
- Planning replay after a logic fix or downstream outage.
- Reviewing state size, checkpointing, and consumer lag.

Do not use for hourly or daily batch movement where a scheduled idempotent job is simpler and cheaper.

## Workflow

### 1. Write the event contract

Every event needs an identity, a time, a key, and a version:

```json
{
  "event_id": "01J8Z3K4T9YQ6R2M5N7P8W1X0A",
  "event_type": "order.placed",
  "schema_version": 3,
  "occurred_at": "2026-11-26T09:14:22.481Z",
  "produced_at": "2026-11-26T09:14:22.902Z",
  "tenant_id": "t-481",
  "order_id": "ord-99231",
  "amount": {"value": "149.90", "currency": "EUR"},
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736"
}
```

`event_id` is globally unique and generated by the producer. `occurred_at` is the business time and is immutable. `produced_at` is when the producer wrote it. Use a schema registry and an explicit compatibility mode: `BACKWARD` lets consumers upgrade first, `FORWARD` lets producers upgrade first, `FULL` requires both. Register the schema in CI before deploying either side.

### 2. Choose delivery semantics per hop

| Semantics | Mechanism | Failure behavior |
| --- | --- | --- |
| At most once | Commit offset before processing | Lost events on crash |
| At least once | Process, then commit offset | Duplicates on crash or retry |
| Exactly once (Kafka) | Transactional producer and `read_committed` consumer | Higher latency and cost |
| Exactly once (Flink) | Checkpointed state plus transactional or idempotent sink | Recovery bounded by checkpoint interval |

For analytics, at-least-once plus deduplication on `event_id` in the sink is usually the right tradeoff. For billing or ledger events, use a transactional sink or an idempotency table keyed by `event_id` inside the same transaction.

### 3. Partition for ordering and throughput

Ordering is guaranteed only within a partition. Key by the entity whose events must stay ordered (`order_id`, `account_id`), not by a random value. Estimate partition count from peak throughput:

```text
partitions >= peak_MB_per_second / sustainable_MB_per_second_per_partition
```

A common planning figure is 1 to 10 MB/s per partition depending on message size, replication, and consumer cost; measure on your own cluster. Watch for hot keys (a single large tenant) and salt only if ordering per key is not required. Partition count can be increased but never decreased without recreating the topic.

### 4. Configure the producer for safety

```properties
enable.idempotence=true
acks=all
retries=2147483647
max.in.flight.requests.per.connection=5
delivery.timeout.ms=120000
compression.type=zstd
```

Idempotence requires `acks=all`, retries greater than zero, and at most five in-flight requests; the client enforces these. It prevents duplicates from producer retries within one session, but not duplicates from an application retry that creates a new event. Set `delivery.timeout.ms` so the producer fails before the upstream caller times out.

### 5. Define event-time windows and watermarks

```sql
CREATE TABLE clicks (
  event_id STRING,
  user_id STRING,
  clicked_at TIMESTAMP(3),
  WATERMARK FOR clicked_at AS clicked_at - INTERVAL '10' SECOND
) WITH (
  'connector' = 'kafka',
  'topic' = 'clicks',
  'properties.bootstrap.servers' = 'broker:9092',
  'format' = 'avro',
  'scan.startup.mode' = 'group-offsets'
);

SELECT
  window_start,
  window_end,
  COUNT(DISTINCT user_id) AS users
FROM TABLE(TUMBLE(TABLE clicks, DESCRIPTOR(clicked_at), INTERVAL '1' MINUTE))
GROUP BY window_start, window_end;
```

The watermark bounds how long the job waits for out-of-order events. A tight watermark lowers latency but drops more late events; a loose one raises state and latency. Set `allowedLateness` explicitly and route late events to a side output instead of discarding them silently.

### 6. Size and checkpoint state

Use keyed state scoped to the entity, with a TTL:

```java
ValueStateDescriptor<Session> desc =
    new ValueStateDescriptor<>("session", Session.class);
desc.enableTimeToLive(StateTtlConfig.newBuilder(Duration.ofHours(24))
    .setUpdateType(StateTtlConfig.UpdateType.OnCreateAndWrite)
    .setStateVisibility(StateTtlConfig.StateVisibility.NeverReturnExpired)
    .build());
```

Prefer RocksDB for state larger than available heap. Set checkpoint interval based on recovery tolerance (commonly 1 to 5 minutes), enable incremental checkpoints, and store checkpoints on durable object storage. Track checkpoint duration, failed checkpoints, and state size; a checkpoint that takes longer than the interval will eventually fail.

### 7. Handle backpressure, lag, and poison messages

Monitor consumer group lag per partition, not just the total. Alert when lag grows for 15 minutes, when the oldest unprocessed record exceeds the freshness SLO, and when processing latency p99 approaches the window size. Scale consumers up to the partition count, then increase partitions. For poison records, retry a bounded number of times with backoff, then publish to a dead-letter topic with the error, stack trace, topic, partition, offset, and original headers. Alert on DLQ depth; an unmonitored DLQ is data loss.

### 8. Plan replay before you need it

Replay requires retained data, a reset offset strategy, and an idempotent sink:

```bash
kafka-consumer-groups.sh --bootstrap-server broker:9092 \
  --group orders-enricher-v2 --topic orders \
  --reset-offsets --to-datetime 2026-11-20T00:00:00.000 --execute
```

Replay into a new consumer group or a new sink table, then swap. Never replay into a live sink that appends without deduplication. Check retention (`retention.ms`) against the replay window; if the window is longer, land a copy in object storage. Compacted topics keep the latest value per key and are suitable for rebuilding state, not for full event history.

## Validation

- [ ] Schema is registered and a compatibility check runs in CI.
- [ ] A restart mid-batch produces no duplicate rows in the sink (test with a forced kill).
- [ ] Late events within the allowed lateness are included; later ones are counted in a side output.
- [ ] Consumer lag alert fires when a consumer is paused for 15 minutes.
- [ ] Checkpoint restore rebuilds state within the recovery SLO.
- [ ] A poison record reaches the DLQ with offset and error context.
- [ ] Replay of one hour of data into a staging sink matches the original counts after deduplication.
- [ ] Partition count and key distribution are checked for hot partitions.

## Gotchas

- Exactly-once in Kafka covers Kafka reads, state, and Kafka writes. A JDBC sink without transactions is at-least-once no matter what the consumer config says.
- Committing offsets before processing loses events on crash. Commit after the sink acknowledges, or use a transactional outbox.
- Producer retries without idempotence duplicate messages. Enabling idempotence does not deduplicate application-level retries.
- Ordering is per partition only. Repartitioning or changing the key breaks the ordering assumption.
- Watermarks advance with the minimum across inputs; one idle partition stalls the whole job. Configure idleness detection.
- A tight watermark plus no allowed lateness silently drops mobile or offline events that arrive late.
- Window results emitted early may be retracted later. Downstream aggregations must handle updates or wait for the final result.
- Consumer group rebalances pause consumption and can repeat in-flight records. Use cooperative sticky assignment and static group membership where supported.
- Total lag hides a single stuck partition. Alert per partition and on oldest message age.
- Increasing partitions does not rebalance existing keys. Old keys stay on old partitions, so ordering and load can remain skewed.
- A compacted topic is not an event log. Replaying it rebuilds latest state but loses intermediate events.
- Deleting a topic or letting retention expire destroys replay capability. Verify retention against the compliance and recovery window.
- Deserializing untrusted Avro or JSON with recursive schemas can exhaust memory. Enforce schema limits and a dead-letter path.

## Output contract

```yaml
pipeline_id: orders-enrichment-v2
source: {system: kafka, topic: orders, partitions: 48, key: order_id}
sink: {system: iceberg, table: analytics.orders_enriched, upsert_key: order_id}
event_contract:
  schema_registry: confluent
  subject: orders-value
  compatibility: BACKWARD
  version: 3
semantics:
  delivery: at-least-once
  dedupe: {field: event_id, store: iceberg_merge}
  ordering: per order_id
event_time:
  field: occurred_at
  watermark: 10 seconds
  allowed_lateness: 2 minutes
  late_sink: analytics.orders_late
state:
  backend: rocksdb
  checkpoint_interval: 60 seconds
  ttl: 24 hours
  estimated_size_gb: 18
operations:
  lag_alert: oldest_unprocessed_age > 5 minutes
  dlq: orders-enriched-dlq
  replay_window_days: 14
  recovery_slo_minutes: 10
```

## Checklist

- [ ] Event contract includes event_id, occurred_at, produced_at, key, and schema version.
- [ ] Schema compatibility mode chosen and checked in CI.
- [ ] Delivery semantics stated per hop, not per system.
- [ ] Sink deduplicates on event_id or is transactional.
- [ ] Partition key matches the ordering requirement.
- [ ] Watermark and allowed lateness derived from observed event delay.
- [ ] State backend, TTL, and checkpoint interval sized.
- [ ] Per-partition lag and oldest message age alerted.
- [ ] DLQ configured with error context and alerting.
- [ ] Replay runbook tested, including deduplication.
- [ ] Retention covers the replay and compliance window.
- [ ] Hot partition and key skew reviewed.
